# HANDOFF — research state as of 2026-10-19

This is the working memory of the project: what has been established, from where, and what is still open. Update it whenever a question is answered. `README.md` is the public summary; this file is the detailed one.

## 1. Thesis

The BC-250 is the same silicon target as the PS5 (Zen 2 + `gfx1013` + 16 GB unified GDDR6). Every existing PS5 runtime targets generic PCs and therefore translates the GPU side (AGC/PM4 → Vulkan, RDNA ISA → SPIR-V). On the BC-250 that translation can be removed: hand the game's command stream and shader binaries to `amdgpu` as-is. Everything else (loader, system libraries, audio, input) is the host: KytyPlus (GPL-2.0), whose system libraries are written independently (HLE) — no PS5 firmware or system-software dump is used, ever (D18, ADR 0012). The console-format command stream is today built by the game's own copies of Sony's `libSceAgc`/`libSceAgcDriver`, LLE-loaded from a game dump's `fakelib/` (D11); an independently written AGC driver in the host is to replace them (Q14). In either form BC5 sits at the `/dev/gc` boundary.

What we deliberately do not do: boot PS5 firmware (PSP/Sony keys/ABL/SMU/hypervisor cannot run on the BC-250; no Sony southbridge, SSD/Kraken, Tempest), load a firmware or system-software dump (D18), write a new emulator, or touch Sony material.

## 4. Architecture (summary)

```
PS5 game (eboot.bin, PRX)  →  KytyPlus host: loader, libkernel and every system library written independently (HLE; D18, ADR 0012)
                               ├ today: the game's own libSceAgc/libSceAgcDriver, LLE-loaded from a game dump's fakelib/ (D11; the pack, Q14)
                               └ next:  an independently written AGC driver in the host (Q14)
                            →  /dev/gc boundary  →  BC5 backend (direct path, ADR 0005/0006)  →  amdgpu/libdrm  →  BC-250
                                                     ├→ I/O layer (bc5-mount: .ffpfsc and .pkg, parallel reads, decode-ahead, disk cache)
                                                     └→ audio + input (host: PipeWire, SDL; haptics as audio to the DualSense's own USB device)
```

One host, one track: RPCSX is a reference for the `/dev/gc` layouts and the PM4 synchronisation packets (F12), not a host (D18). The backend's host interface is the `/dev/gc` boundary (F12, F18): submit ioctls, GPU memory mapping (`mmap`, flexible/tool memory), `kevent` completion, EOP flip and buffer labels. Whatever builds the command stream behind that boundary — the LLE pair today, the host's own driver tomorrow — gets the same backend.

Backend modes: (1) validation — decode + log, submit nothing (the captures of experiments 0011–0012); (2) hybrid — never built; (3) direct — own libdrm client, the guest's memory mapped 1:1 as dma-bufs of the host's backing files (ADR 0006), the packets filtered and rewritten for `amdgpu`'s command processor (the context-state stack, the label hand-overs, CP DMA waits: F34–F42), jobs in flight on the GFX ring with the title's asynchronous compute on the BC-250's compute rings (ADR 0009, F177–F181), graphics pieces behind a full-state prefix at cross-queue waits (ADR 0008), a register-state prefix before drawing buffers against state inherited from the desktop (F204), and submission chains behind `BC5_DIRECT_CHAIN` (ADR 0010, F213, F218). Everything that submits is behind `BC5_GC_MODE=direct` and `BC5_DIRECT_STAGE` (hard rule 5).

CU policy: D5's 36/4 split exists as a switch (`BC5_DIRECT_CU_MASK`, ANDed with the masks the titles write, F39/F39a) and is in no play setting; both titles run on all 40 CUs (F97, Q8).

## 7. Decisions taken so far

- D1 Project name **BC5** (BC-250 + PS5). Repo `bc5`; fallbacks `bc5-native`, `bc5-agc` if taken.
- D2 License GPL-2.0 (RPCSX compatibility).
- D3 Public, English, anti-piracy: no Sony material, bring your own console and dumps, no warranty.
- D4 Start with the input layer (`bc5-mount`) before anything GPU-related.
- D5 36/4 CU split as a backend switch, measured in phase 3.
- D6 Tools in Rust, backend in C++20 (RPCSX is C++).
- D7 (2026-09-29) Phase-1 preparation that needs no hardware and no game (Q2 research in the RPCSX sources, `docs/formats/agc.md`, the `bc5-agc` PM4 decoder with hand-built streams) may proceed before gate G0a is recorded, because it does not depend on `bc5-mount`. Phase 0b, anything under `backend/` and anything that submits to the GPU still wait for their gates. Maintainer's decision; overrides the "one phase at a time" rule of `CLAUDE.md` for this case only.
- D10 (2026-09-29) Prosper (github.com/mattias800/prosper, commit `1c93ab8`) is used **locally on the dev box as an external capture tool** while no firmware dump exists: it runs ASTRO BOT to its title screen without PS5 system modules. Prosper has **no licence**, so none of its code, text or data enters this repository, and nothing derived from it is distributed. It is built from source in the `ubuntu` distrobox (`~/src/prosper`, build in `~/bc5-work/prosper-build`) with one **local-only** patch (`~/bc5-work/prosper-bc5-dcb-dump.local.patch`, 24 lines in `hle_agc.cpp`) that writes each submitted DCB as raw dwords to `$BC5_AGC_DUMP_DIR`; its own `PROSPER_SHADER_DUMP` provides shader binaries. Captures live in `~/bc5-data/captures` and are never committed; experiments record only statistics produced by our tools. Caveat for every result: part of each DCB is written by Prosper's HLE of `sceAgcDcb*` rather than Sony's library, so captures describe "game + Prosper", not a console byte stream. Maintainer's decision.
- D11 (2026-09-30) **The host runtime becomes pluggable; track B is opened.** Following F16–F18: (1) the BC5 backend gets its host interface at the `/dev/gc` boundary (submit ioctls, `mmap` of GPU memory, flexible/tool memory, `kevent`, EOP flip, buffer labels), so any host that provides those calls can drive it. (2) Track A — RPCSX with the maintainer's own firmware dump — stays the reference path and keeps gate G0b. (3) Track B — KytyPlus (GPL-2.0-only, licence-compatible) with the game's own `fakelib/libSceAgc.sprx` and `libSceAgcDriver.sprx` LLE-loaded from the maintainer's dump. First task: implement in KytyPlus the 29 imports of experiment 0010 so that Sony's driver initialises, and route the `/dev/gc` ioctls to a capture buffer; that yields the first DCB built by Sony's code. KytyPlus changes are kept as patches under `backend/kytyplus-patches/` and may be offered upstream as PRs. (4) Phase 1 no longer depends on firmware: its captures come from track B. Prosper (D10) is retired as a capture source. Maintainer's decision, approved in chat ("ok - działaj, zatwierdzam").
- D9 (2026-09-29) Phase-2 preparation (ADR 0004: PM4 builder, memset IB, `dispatch-min` with `--dump-ib`/`--info`) may proceed before gates G0b and G1, because phase 0b is blocked on the maintainer's firmware dump and the preparation submits nothing. Running `dispatch-min --submit` still needs the maintainer's explicit go-ahead with the box idle, each time. *2026-09-30: first go-ahead used; experiment 0008 passed (phase 2 task 2 done), one encoder bug found and fixed on the way.*
- D8 (2026-09-29) BIOS memory split: **512 MiB VRAM carve-out** (amdgpu: VRAM 512M, GTT 7596M; Linux sees 14 GiB) instead of the 8 GiB carve-out recorded in experiment 0003. Rationale: the PS5 memory model is unified and phases 2–3 map guest memory as system RAM (userptr/GTT, Q1); RPCSX needs host RAM for the 16 GB guest address space. Risk: Vulkan paths that insist on a large device-local heap; if VSH boot (phase 0b) fails on memory, compare splits in a dedicated experiment.
- D12 (2026-10-01) **`ttm.pages_limit=3407872` (13 GiB) on the dev box's kernel command line**, set by the maintainer after runs 96–99 (F44–F47): amdgpu now reports 13,312 MiB of GTT instead of 7,597 (`mem_info_gtt_total` = pages limit × 4096 before and after, which settles the `TODO(verify)` of F44 by measurement). Rationale: the game reserves 12.4 GiB of direct memory and a draw's BO list names all of it that holds data. Risk: with 15.2 GiB of RAM, pinned game memory leaves little for the rest of the system; undo with `rpm-ostree kargs --delete=ttm.pages_limit=3407872`.
- D13 (2026-10-06) **After a cold boot the BC-250 comes up with 6 cores / 12 threads; a warm reboot is needed for 8 / 16.** The 8-core unlock service sets an SMU mask that a warm reset keeps and a power cycle loses, and it only re-arms the mask for the next reboot. Boots of 2026-10-02 08:43 and 2026-10-06 16:11 ran on 12 processors (run 117 and the pad tests); the boots of 2026-10-01 had 16. Check with `nproc` before a measurement; the fix is one reboot. Source: `journalctl -b <n> | grep smpboot` and the unlock script's own comment.
- D14 (2026-10-06) **Controller mapping is a text file, not an environment variable per case.** KytyPlus had `--keymap Control=Input` (keyboard, mouse, pad buttons as sources for the host-input stream) but no way to disable a physical pad input and no file. Patch 0001 adds `--input-config <file>` / `KYTY_BC5_INPUT_CONFIG` with the same grammar plus `Pad:<button|axis>=none`, pad axes as sources (`Pad:righttrigger`, `Pad:leftx-`) and `DefaultKeys=on|off`; the built-in keyboard layout stays unless a line takes a key or a control from it. The maintainer's immediate case (a pad whose R2 is stuck: `Pad:righttrigger=none`, `R2=O`) is two lines of `~/bc5-work/input.cfg`, named from `bc5-run.env`. Reference: `backend/kytyplus-patches/input.example.cfg`. 2026-10-08: the same file is edited from a menu in the game window (F2; `settingsOverlay.cpp`, ImGui in the presentation pass beside the IME keyboard, the simplest version first as decided with the maintainer): bind by pressing the input, pad inputs to ignore, the built-in layout, Apply live, Save to the file. The map holds the live configuration behind one mutex and is replaced whole on Apply; a bad line leaves it untouched and is shown. Confirmed by the maintainer in the game on 2026-10-08: F2 opens it, Bind takes the pressed input.
- D15 (2026-10-09) **Per-title settings for the direct path, in the title's launcher, not in the shared `bc5-run.env`.** A title's GPU heaps (`BC5_DIRECT_EAGER_NAMES`, by the names the title gives them) and its learned-fault file (`BC5_DIRECT_LEARNED`) belong to that title: the second title's learned windows had been written into ASTRO BOT's file (51 entries, removed). The second title's launchers are `run-pkg.sh` and `play-pkg.sh` (experiment 0037), the latter behind a desktop shortcut.
- D17 (2026-10-19) **The emulator window has a menu bar; the host still mounts nothing** (ADR 0011, experiment 0164). An ImGui menu bar (File: Open game image / Open package / Recent / Close session / Quit; Emulation: Pause, Restart, Settings, Fullscreen; Help: About) drawn in the settings overlay's pass, `kyty_emulator --menu` for the empty window with a launcher page, F1 or the pad's PS button during play. Opening and closing are exit codes like the F2 menu's 75: 76 = open the path in `$KYTY_BC5_MENU_DIR/choice.txt`, 77 = close the session; `play-any.sh` on the dev box loops over them and hands a `.pkg` to `play-pkg.sh` and a `.ffpfsc` to `play-astro.sh`, so the mount, the system-module pack and the per-title switches stay where D15 put them.
- D18 (2026-10-19) **The host does not use a PS5 firmware or system-software dump, and never will; every system library is written independently in the host** (ADR 0012). After the work of experiments 0154–0164 it is clear the project will not take the RPCSX road (booting the console's system modules): everything both titles needed was written in the host from public symbol names and the titles' own calls, following KytyPlus's model, and that is the rule from here. Track A of D11, phase 0b and phase 4 are retired; RPCSX stays a reference for the AGC/GPU side only (§6). The maintainer's own decrypted system-software root (`~/bc5-data/ps5-fw`) is private reference data: nothing is loaded or derived from it. The system-module pack (`SHADPS4_SYSMODULES_PACK_DIR`), today a copy of a game dump's `fakelib/` — `libSceAgc`, `libSceAgcDriver` (the LLE pair of D11), `libScePlayGo`, `libScePsml` — is to be phased out of the launchers as the host's own libraries cover what it provides, PlayGo and Psml first, the AGC pair last with an independently written driver (Q14). Maintainer's decision, stated 2026-10-19.
- D16 (2026-10-09) **Conversions that make the GPU execute work it never executed are off by default and tried one short run at a time, with the build synced to disk first.** Run 64 (F90) showed that such a change can take the machine down, and that a hard reset loses what was written just before it (the backend library came back empty). The compute-form `DISPATCH_INDIRECT` conversion stays behind `BC5_DIRECT_MEC_INDIRECT=1`; the second title's launchers turn it on with its one hanging program skipped (F91), after it ran clean in short, watched runs.
