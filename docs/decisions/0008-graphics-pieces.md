# ADR 0008 — Graphics buffers split at cross-queue waits, with their state replayed

**Status:** accepted (2026-10-14). Steps 1–4 passed (experiments 0072–0078): in the water the pieces remove the given-up waits and broken cycles, the fluid is on time, no fault. `BC5_DIRECT_PIECES_FULL=1` is on in the play settings; making it the default is the remaining step.

## Context

Water in ASTRO BOT is two cycles between the game's graphics and compute queues (HANDOFF F64,
ADR 0005 xxii):
1. The main graphics buffer waits at dword ~115 for a label of the compute buffer.
2. The compute buffer's fluid tail waits for a label the main graphics buffer sets at ~1,588.
3. The main graphics buffer then waits again, at 11,000–20,700, for that fluid tail.

On the console the two queues run side by side. Here there is one ring, and the host serves
every wait of a graphics buffer on the CPU before the whole buffer goes. The second cycle
therefore cannot be served. The stopgap (8 ms limit, cycle break) lets the fluid reach the
picture a frame late. In the water this gives ~500 waits given up and ~50 broken cycles a
minute, at 43–52 fps (sessions of 2026-10-13).

Compute buffers are already split at every wait, with their register-setting packets replayed
before each later segment (`acb-state`, run 122: 44,028 jobs, none failed). The same for graphics
buffers (`BC5_DIRECT_PIECES=1`) faults from the first frames: run 123, a shader fetch at
`0x800000005000`, the same as run 44. The machine went down in run 123.

The likely reason, from run 44: between two pieces other processes' work runs on the same ring
(the desktop compositor, KytyPlus's own Vulkan presentation). It leaves its own SH and UCONFIG
registers behind, and the CP does not restore ours.

## Decision (proposed)

Split a graphics buffer at a cross-queue wait only when the wait cannot be served before the
buffer goes (the second cycle). Before each later piece, emit the full register state the
piece's packets rely on, generated by the backend's tracker rather than by replaying the
packets:

- **context registers**: already tracked for pops (`bc5::state_stack::Tracker`, ADR 0005 xix);
- **SH registers** (`SET_SH_REG`, `LOAD_SH_REG[_INDEX]`, shader program addresses, user data):
  to be tracked the same way;
- **UCONFIG registers** (`SET_UCONFIG_REG[_INDEX]`, `LOAD_UCONFIG_REG_INDEX`, primitive type,
  index type, number of instances);
- **non-register state** set by packets: `SET_BASE` (both indices), `INDEX_BASE`,
  `INDEX_BUFFER_SIZE`, `INDEX_TYPE`, `NUM_INSTANCES`, `CONTEXT_CONTROL`.

The prefix begins with `CONTEXT_CONTROL` (load enables) and a `CLEAR_STATE` cmd 0, so nothing
left by another process survives into the piece.

The alternative is the CP's register shadowing, as Mesa sets it up (`ac_create_shadowing_ib_preamble`,
gfx10 branch). It is untested on gfx1013. It needs a shadow buffer registered with the kernel,
which user-mode submission here does not control. Second choice.

## Plan, in order of risk

1. **Offline, no GPU.** Extend the tracker to SH, UCONFIG and the packet state above. Unit tests
   with synthetic buffers. Then, over the dumped graphics buffers (private; 60 of a later level
   from experiment 0061, and new ones of the water):
   - decode each buffer in full and record the register state at every cross-queue wait;
   - emit the prefix for that point and decode prefix + rest;
   - require every draw and dispatch after the split to see the same registers as in the
     unsplit buffer;
   - record differences in a new experiment.
2. **Map-only run** (no GPU submission): the host builds the pieces in the water. Count pieces,
   prefix sizes and the time per frame.
   Done outside the water (experiments 0074, 0075): almost every wait not satisfied on arrival is
   left to the GPU by ring order. In the water (experiment 0076) a split is needed about 0.4
   times a frame.
3. **GPU, outside the water, with the maintainer present.** Prepared, not run:
   `BC5_DIRECT_PIECES_FULL=1` in the KytyPlus patch. Passed (experiment 0077): 20 pieces, no fault. Split the main buffer at its first
   wait even when that wait is already satisfied, so the pieces run where nothing else changes.
   Use the hang watcher and the devcoredump (experiment 0058). One run, then compare the
   picture.
4. **GPU, the water, with the maintainer present.** Measure given-up waits, broken cycles,
   frame rate, and whether the fluid is still a frame late.

Each step goes to the next only after the previous one is recorded as passed.

## Consequences

- If step 1 shows that the tracked state reproduces every draw's registers, the run-123 class of
  fault has a concrete remedy to test. If it does not, the differences name what is missing,
  without a GPU run.
- The 8 ms limit and the cycle break stay as the fallback.
- Cost per piece: a prefix of a few hundred to a few thousand dwords. In the water that is a few
  pieces a frame.
