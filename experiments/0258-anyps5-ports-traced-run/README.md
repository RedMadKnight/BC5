**Result.**
- **The route worked.** L1: title → slot list → CONTINUE GAME menu (t 70 s) → black load screen (t 80 s) → the lake outpost with the "Parry" prompt at 95–140 s. D1: the same list, then after △ ✕ the list at t 110 s shows `NEW GAME 3 — EMPTY` with Saved Game 1 (19/10/2026 18:02) and 2 (22/10/2026 10:43) intact.
- **F217, search, patterns and params: as designed.** Each visit of the slot list makes nine `sceSaveDataDirNameSearch` calls, each with a pattern that selects one slot's save kind (the hits per search are `i38-slot<N>-game-autosave`, `…-settings-autosave`, `…-game-manual-1`, `…-game-snapshot-*`: the `%`/`_` matching works; `i38-null-prefs` answers the unpatterned search). Every hit carries `user_param 0`, the `.param` mtime (the dates the list shows are exactly the `.param` mtimes, e.g. 18:02:42 → 18:02), `blocks 16384` and `free 16366–16382` (one to eighteen 32-KiB blocks used by the files). `L1-trace-lines.txt`, `D1-trace-lines.txt`. The `.param` sidecars themselves were written by the ported `SetParam` during the maintainer's play since 10-19: the lake copy of 10-22 11:52 already has one per directory.
- **F217, delete: the directories go, the sidecars stay.** D1's `SaveDataDelete` removed the slot's four directories (`i38-slot3-game-autosave`, `-game-manual-1`, `-game-snapshot-52266`, `-settings-autosave`, "removed 3 entries, error 0" each) inside the F205 dialog sequence (Initialize, Open mode 5 disp_type 3, status 2, 101–103 `ProgressBarSetValue`, Close, status 3, Terminate; twice), and the list shows the slot empty. But the four `i38-slot3-*.param` files are still in the private copy after the run (`D1-sidecars.txt`).
- **F217, `.blocks`: written inside the save.** No `<dir>.blocks` sidecar appeared next to any directory. Instead the private copy holds `i38-null-prefs/.blocks`, `i38-slot1-*/.blocks`, `i38-slot2-*/.blocks` (from the lake copy) and the live saves hold ten such files (`i38-slot1/2/3-*/.blocks`, `i38-null-prefs/.blocks`), written by the host's `Mount3` since the 10-19 binary.
- **The cause of both:** `Common::FixDirectorySlash` (`src/common/stringUtils.h`) appends a `/`. `save_data_keep_blocks(FixDirectorySlash(mount_dir))` therefore wrote `<dir>/.blocks`, and `remove(param_path(FixDirectorySlash(dir)))` aimed at `<dir>/.param`, which never existed. `SetParam`, `GetParam`, the search and `GetMountInfo` built their paths as `root + "/" + name` and were right (the double slash from the root's trailing `/` is harmless). Fixed in this branch's patch 0001: the three sites use `FixFilenameSlash` (no trailing slash) and the title root has none either; the patch regenerates byte-identically over main's except those lines. Not built yet. The stray `<dir>/.blocks` files in the live saves (one 32-KiB block each in the used count; the title has not been seen to react to them) need a cleanup the maintainer approves: `find ~/bc5-work/_SaveData/PPSA03671 -mindepth 2 -name .blocks -delete`.
- **F215, NpManager: not exercised.** Zero `callback =`, `callback_id =` or `state callback` lines in either run: through the title screen, the slot list, a load and the first minute at the outpost, the title registers no Np state callback, so the port's delivery path did not run. (The port's lines are unconditional `LOGF`s; the library name log stays silent in play mode, exp 0256.)
- **F216, NpTrophy2: weak positive again.** Zero `Unresolved import stub called` / `stubbed import` lines in either run; nothing names trophies.
- **F214: idle as in F314.** The vibration port rode the DualSense's sink (`type 10 2 ch (pad)`, `device playing` in every trace line of both runs); the fallback had no reason to run.

**Verdict.** Passed for the search half of F217 and the F205 delete path; failed for the sidecar paths, with the cause found and fixed in the patch (pending a build and one more delete run to see the `.param` and `.blocks` files go).
