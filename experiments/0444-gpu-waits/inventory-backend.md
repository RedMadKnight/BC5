## 3. HANDOFF F898-F903 (main `docs/HANDOFF.md:881-886`)

- **Chained frames.** The third title's frame is one dcb chained through dozens of segments (73 in the earlier frames; the 10:42 scene dcb had 98 pieces). Three host defects of one class: the writer scan reads the top level only (F899), the system-prefix draw test reads the top level only (F901, fixed by pc439, not the stall), and the filter drops every piece wait whose label its own piece does not write while the host's wait handling never sees piece waits (F902). So no cross-queue wait of a chained frame reached the GPU or the host. F899's evidence: acb 3452's waits at 62, 235 and 2749 were met in memory at submit and dropped while their dcb writer was in flight ("writer in flight 0").
- **Kept GPU wait vs host hold (F902).** With pw439=2 every piece wait went to the GPU, and the title hung at ~4 s: the dcb's GPU wait needed a label from an acb the host was holding (`acb_ready`, U5) until a later label of that same dcb. HANDOFF's conclusion: the console order cannot be restored on one side only; either the host stops holding acbs, or a piece wait is kept only when its writer is already in a kernel ring.
- **The stall (F898, F900).** Every clean-boot run stalls at the title's first 3D gameplay frame, on both system images; the earlier "8 of 8 passed" never reached it. In-time wave scans found no resident wave while two compute queues stood behind dispatches (clouds acb behind a DISPATCH_INDIRECT, queue 16's shadow buffer behind its second). F900: that frame's dcb is the first BVH build on the GFX queue (80 GFX-form DISPATCH_INDIRECT with GPU-filled count records, no PFP_SYNC_ME in that piece), the second title's hang family; its host measures are second-title-only defaults (kTitleDefaults) and off here. Cause: hypothesis.
- **Capture (F903).** No capture landed inside a stall until 11:18 (late umr launch, a global watchdog slot reset by every ring, a blocking unmet-wait list); `amdgpu.lockup_timeout=10000` is set on the dev box since the 11:04 boot.
- **Queue count.** F898-F903 speak of "two compute queues" stuck in the hang. The exp 0439 README gives the fuller picture (not in those rows): 56 guest compute queue rings registered (README:158); the busy ones map queue 16 -> libdrm compute ring 2, queue 24 -> ring 1, queue 40 -> ring 3, and every queue starts on ring 0 and moves only after 256 jobs (README:377, :515-516; `w428_queue_ring`). With 4 kernel compute rings (`direct.hpp:23-24`) plus GFX, early frames put several guest queues on one ring.
