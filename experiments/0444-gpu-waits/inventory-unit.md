## The label writes the host itself makes

These must stay correct (or be moved to the GPU) when the GPU decides the waits:

- **Flip labels `g_labels[64]`** (339; handed out by `GetBufferLabelAddress`, 17801-17806). Cleared to 0:
  - by "bc5-fliplabel" after `Bc5VideoOutWaitFlipDone` (17904-17918);
  - directly when the flip fails (17898);
  - in the deferred mode (`BC5_DIRECT_FLIP_DEFER`) by "bc5-flipdone" after `Bc5VideoOutWaitFlipCopied`, with `g_flip_pending` (17838-17868);
  - **and forcibly at a wait** (10549-10550, H11).

  When the GPU polls these labels, the clear must be a store the GPU sees (userptr guest memory, so yes). The forced clear must be removed.
- **Soft-CP replays of GPU-dropped packets** (`execute`, 1494-1500): WRITE_DATA, COPY_DATA, ATOMIC_MEM, and RELEASE_MEM / EVENT_WRITE_EOP data are written by the CPU when the packet is **not** marked GPU-executed (`!done`). Also R3 G2 MEM_SEMAPHORE signal (1506-1512) and G11 COND_WRITE (1513-1519): in lean both are on via `BC5_LEAN_OR(true, ...)` (794, 798); in the normal build only when `BC5_R3_MEMSEM_SIGNAL` / `BC5_R3_COND_WRITE` are set. These run **after** the job's fence (post, 15147), so a GPU wait on such a label sees it late, only after the CPU replay. Any label whose writer packet the filter drops is written only by the CPU.
- **EOP interrupts:** `fire_eop` (707-719) fires EVFILT_GRAPHICS idents 0x40 and 0x00 (gfx), or 0x48 and 0x46 (compute). It runs from the soft CP for **every** RELEASE_MEM / EOP with INT_SEL ≠ 0, GPU-executed or not (1331-1333, 1343-1345). Compute vs gfx is guessed from `qq.a == 2` (1743, TODO). These are host events on the replay's timeline, not the GPU's.
- **Submit-and-EOP ioctl 0xc020810c:** writes `eop_value` to the submit-done page (17067-17072). The G6 EOP event is removed (797: `submit_eop = false`).
- **Doorbell read pointers:** published at `rptr_addr` and at `ring_end` after the replay (1764-1765). These are not labels, but the title's free-space check reads them.
- **Label presets:** none in this unit (see "Not found").

## Ring mapping as it is today

- **Default (`BC5_DIRECT_ACB_RINGS` unset or 0):**
  - `compute_ring_env()` returns `BC5_DIRECT_COMPUTE_RING` (DIAG, so not in lean) or `kGfxRing`; `acb_ring` gives `kGfxRing` for `ring < 0` (7569). The value of `kGfxRing` is in the backend header (inferred negative, unverified).
  - So **every acb of every guest queue and every dcb of every game thread go to the one GFX ring.** Guest queues share one ring; "cross-queue waits on one ring" (7304-7309) is the reason for H1-H17.
  - `ring_will_satisfy` counts only same-ring writes (10321).
- **`ACB_RINGS = 1`:** `w428_queue_ring` is not called (7570 needs > 1), so all acbs go to compute ring 0. All guest compute queues share ring 0.
- **`ACB_RINGS = n ≥ 2`:**
  - Every guest queue (`t_queue_idx`, the bc5-ring consumer's index of the queue registration, 1627) **starts on ring 0** (7484-7488).
  - When its acb count reaches 256 it is "busy" and moves **once** to ring `(++g_w428_busy) % n`, after a 2 s wait-idle (7499-7511). The comment at 7479-7483 says 56 queue slots are touched at start.
  - So **quiet queues share ring 0**, and busy queues rotate 1, 2, 3, 0, ...: several queues can share a ring, including ring 0 with all the quiet ones.
  - The mapping is **re-picked once per busy queue** during the run, not fixed at start.
- **Per-buffer fallback:** `bc5::policy::compute_ring_refusal` (7571) sends any acb it refuses to the **GFX ring** (7582), with the reason counted (7575-7581). `BC5_DIRECT_ACB_MEC_INDIRECT` narrows the "indirect dispatch" reason only (7534-7556). So one guest queue's buffers can be split across its compute ring and the GFX ring, and **in-queue order across those two rings is not guaranteed by the kernel.**
- **dcbs always go to the GFX ring** (`job_ring`, 7584-7586). Per-ring submit order is kept by `g_su436_ring_mu` (15613, 15644-15646).
- **Hardware queue:** the comment at 7464-7465 (exp 0427) says a libdrm ring index is not a fixed hardware queue (the kernel's scheduler re-picks one when the index is idle). Registers therefore do not persist per guest queue, hence the prefixes in H25. A kept GPU wait blocks a kernel ring/entity, which may carry other guest queues in this mapping.
- **Strings:** "queue->ring" is only the stderr counter line (16494). There is no `ACB_QUEUE_STATE` mapping: `BC5_DIRECT_ACB_QUEUE_STATE` is the aq424 register prefix (9137-9147), not a ring mapping.

**What must be true before removal:** each guest queue (and the gfx queue) is bound to its own ring for the whole run, with no move at 256, no ring-0 sharing and no GFX fallback, and the rings run concurrently. Otherwise a wait kept on the GPU can block its own writer: today's one-ring deadlock (7304-7309).
