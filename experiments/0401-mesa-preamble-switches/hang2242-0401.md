# The 2026-11-09 22:42 hang, read on the laptop (exp 0401, water session)

The analysis was asked for by the top session, on the maintainer's "Tak". It is laptop only, with no box access and
no build.

**The captures** are outside git, in `Downloads/bc5/captures-20261109-hang/`:
- `20261109-224227-devcd1.txt` (the devcoredump);
- `direct-slice.txt` (direct.log lines 199250–199460);
- `play-tail.txt` and `dmesg-tail.txt`;
- the ib-timeout `.bin` files;
- `hang-20261109-gdb.txt`.

None of them goes into git; only numbers are quoted here.

**The run:** the "e10 unpacked" shortcut, binary exp0409 (e8 + the AMM scatter, which was off), 13,824 MiB, ~39 min
of play. A `gfx_0.0.0` timeout came on job dcb #2676753 (21,658 dwords, 77 label writes, 0 dispatches). The ring reset
succeeded and the reopen was ok, but the title never drew again.

## 1. The class of the hang: F686/F443's family (a shader reading through a bad address), not the 19:54 fast-launch class, not F403 — medium

| Register | 22:42 | F686 near-class (e9l1, e9n4) | 19:54 draw class | F403 (e8, e9z1) |
|---|---|---|---|---|
| GRBM_STATUS | 0xa04030a5 | 0xa0403028 | 0xa27100ac | 0xa0407028 |
| GRBM_STATUS_SE0/1 | 0x08000006 | 0x08000006 | 0x0d000000 | 0x0a000016 |
| PFP / ME | 0xea1 / 0xe15 | 0xea1 / 0x77b | — / 0xb8b | 0xea1 / 0x77a–0x77b |
| CP_STALLED_STAT1 / 2 | 0x04008c00 / 0 | — | 0x01000c00 / 0x00211000 | — |
| VM fault | SQC (data) reads at 0x18b38000 and 0x18b43000 (dmesg); the devcoredump's cached page 0x706ab000 | SQC inst / TCP at page 0 | none | none |

- **Against F686.** The busy set and SE status are F686's. GRBM_STATUS differs only in CMDFIFO_AVAIL (5 against 8)
  and ME0PIPE0_CF_RQ_PENDING. ME stood at 0xe15, as in exp 0379's D2/D4 pre-menu hangs (which had TCP read faults),
  not at F686's 0x77b.
- **Against the other two.** The 19:54 class has GE/PA/SX busy, SE 0x0d…, and no fault. F403 has SE 0x0a000016 and no
  fault.
- **What the probe shows.** It walked the dcb to op 0x49 at dword 21650, a label write of 1 to 0x11e0db0018, and read
  "now 0x0": the last label did not land.
  - The draws just before it are non-fast-launch NGG (stages 0x02002000, ES 0x11d0125d, prim 4).
  - Earlier in the same dcb, fast-launch draws (stages 0x00482030, ES 0x11d0132d) are marked "ran". Their s[20:23] user
    data point at 0x1100000000, whose 64 bytes read all zero.
- **Not identified:** which shader faulted. The dump has no wave PCs. A zero descriptor table (base 0 + index ×
  stride) would explain loads at 0x18b38000…0x706ab000, but that is a lead, not shown.

## 2. The fault at 0x706ab000: the hang's cause, a garbage address, wrongly learned — high for the order, medium for the rest

- **Order.** dmesg logs the SQC faults at 18587.241 s and the timeout at 18589.300 s. The fault came 2.06 s first: the
  fence timeout.
- **Several faulting pages.** MORE_FAULTS=1. dmesg prints 0x18b38000 three times and 0x18b43000 twice. The
  devcoredump's cache holds 0x706ab000, status 0x00601431 in all.
- **A garbage address.** All three are low addresses (0.4–1.8 GiB). This title's heaps, user data and code all lie at
  0x9_0000_0000 and above (s[8:11] bases 0x11_22…, code 0x9_03f…). TODO(verify) against the run's memory map.
- **The learned-window logic made a junk window of it.** In recover_after_timeout the journal says `learned: fault
  0x706ab000 -> region 0x6e000000+0x6000000 (saved)`, so it was saved into the live learned file.
- **Earlier junk.** After the reopen the scratch list shows earlier windows of the same kind: 0x0+0x6000000, and
  dozens of windows at addresses above 2^44 (0x125652000000, 0x7ffffe000000, …).
- **Their cost.** Each junk window costs a scratch map at every start and learns nothing. A missing import was not
  the cause here.

## 3. Why the title did not resume after "reopen: ok" — medium-low

The journal after the reset:
- Three queued jobs came back `FAILED rc -125` (-ECANCELED, the old device's queue), each after 15.13 s: #2676754 (dcb
  19,499 dw), #2676755 (acb 84 dw) and #2676756 (acb 140 dw).
- Soft-CP replayed one buffer on the CPU: `dcb 20385 dwords at 0x11e0db0050 replayed in full after a failed
  submission`. That is likely the timed-out job's guest buffer, since 0x11e0db0018 sits just before it.
- **No acb was replayed.** The replay path (`chain_post_soft_locked`, unit e9 :6114–6125) posts the chain's
  soft-entries. Nothing in the journal says the two failed acbs or their label writes were replayed.
- **Then nothing more was submitted.** The direct mapper re-imported 40 BOs (11,950 MiB). GTT then stayed at
  2,410–2,412 MiB from t 2370 s onward, because no command submission validated a BO again. Flips stopped.

What gdb shows (5 min after the reset):
- kyty-gpu waits on its condition variable, so no work is queued.
- Both bc5-ring threads sleep, and bc5-chainwd waits on `g_chainwd_cv`.
- The title's Render Thread sits in guest code at 0x903f0d31e, not in any host wait.

**The most likely reading:** the title waits, in its own code, for a value one of the lost jobs should have written.
- The candidates are the labels or end-of-pipe writes of the two cancelled acbs, which were never replayed.
- Another candidate is a label of the timed-out dcb, if the soft-CP replay did not cover it. Whether it did is not
  journaled.
- **Not shown:** the awaited address. gdb took a backtrace only, no registers.
- Earlier reopen recoveries resumed after ~14 s. Whether their failed jobs were dcbs only was not checked here.

## 4. Fix candidates and catchers for one next build (each its own switch, default off)

| Switch | Kind | What it does | Risk |
|---|---|---|---|
| `BC5_DIRECT_RESET_REPLAY_ACB=1` | fix | After a reset, replay on the CPU every job that failed or was cancelled, acbs included, in submission order, as dcbs already are. | A job's results are marked done though the GPU never ran it: a frame of garbage, not a dead game. |
| `BC5_DIRECT_RESET_LABELS=1` | fix (narrower) | Write only the lost jobs' label and end-of-pipe data writes (WRITE_DATA, RELEASE_MEM / EVENT_WRITE_EOP data) after the reopen, in order. No other replay. | The same, smaller. |
| `BC5_DIRECT_RESET_LABEL_JOURNAL=1` | catcher | At the reopen, journal each lost job's label writes (address, value, job, kind). After 5 s and 30 s, journal whether memory holds them. | Log only. |
| `BC5_DIRECT_STUCK_AFTER_REOPEN=<s>` | catcher | If no flip comes s seconds after "reopen: ok", take the guest threads' registers read-only (freeze-dump.sh's gdb, for every thread, not only hot ones). For each register that points into guest memory, journal the 64 bytes there, and match them against the previous switch's addresses. | Read-only. gdb stops the process for a moment. |
| `BC5_DIRECT_LEARN_GUEST_ONLY=1` | fix | A fault address that lies in no guest view is not learned or saved. Instead the journal gets "fault outside guest memory: not learned". | A real fault in a not-yet-listed view would be missed once. The view list is rebuilt before the check. |
| `BC5_DIRECT_FAULT_PAGES=1` | catcher | At a timeout, journal every fault page the kernel reported since the job started (dmesg is read by the host already for the learned logic), not just the cached one. | Log only. |

**Separately, his yes only:** a one-off cleanup of the live learned file's junk windows (0x0, the addresses above
2^44, 0x6e000000), keeping a backup. It would remove a scratch map per junk window at every start.
