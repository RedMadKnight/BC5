What was compared:

- *The zero user-data pattern.* The hung draws of both hangs, and every draw issued after them, have GS user data

- *Inputs.* The arguments and the first 32 bytes at s[8:9] were identical at CP time, submit and now.
- **Conclusion: nothing in the captured state or data separates the hung draw from healthy ones.** A race on its
  arguments or its s[8:9] data is excluded for those 48 bytes (High). Data the ES reads elsewhere is not captured.

**Both hung draws were the first fast-launch draw after other work:**
- 22:54's 12037 followed non-fast-launch NGG draws (stages 0x02002000; the last at 11959).
- Here, 1702 is the title dcb's first draw, after the host prefix and the preceding jobs #412349–#412351, which have no
  fast-launch crumbs.

Two of two, but such transitions happen many times per frame. It is a fit, not a proof (R21).

**A sourced hardware lead (Mesa 0866ae7).** The dcb's numbers fit it; it is not shown.
- `src/amd/common/ac_gpu_info.c:409-411`: "Some GFX10 chips can hang when NGG exports zero vertices and primitives.
  The workaround is to always export a single degenerate triangle." The flag is `has_ngg_fully_culled_bug` for
  `gfx_level == GFX10`, and line 341 says that GFX1013 is GFX10 plus ray tracing.
- `ac_nir_lower_ngg_gs.c:819`: "When the workgroup emits 0 total vertices, we also must export 0 primitives
  (otherwise the HW can hang)".
- `radv_shader_info.c` (the mesh notes around line 783): "with GS_EN=1 we must also set VGT_GS_MAX_VERT_OUT
  (otherwise the GPU hangs)".
- Mesa uses `GS_FAST_LAUNCH` only for mesh shaders (`radv_cmd_buffer.c:4168-4171`).

**H1.** A meshlet subgroup of this pass that culls everything (0 vertices, 0 primitives) hangs the GE on gfx1013.
The title's PS5-compiled shader would lack Mesa's workaround. H1 fits:
- the rarity, which depends on the view;
- several ES programs of one pass;
- sane inputs;
- GE/PA/SX/SPI busy with SC idle.

Evidence: Low. Whether these ES programs can request 0/0 is a question for their code (Proposed switches, A3).

### 3. The acb #412364 never started: it was queued behind the dcb on the same ring

**It ran nothing.** Its dump has 11,840 dwords, against 11,130 submitted. The dump begins with a 62-dword host
compute-state prefix (dwords 0–61); the rest of the difference was not traced.
- It sets `COMPUTE_PGM_LO` itself at 162 (0x11d04f80) before its first dispatch at 210.
- The probe's summary counts 434 dispatches, 142 of them indirect. Its 342 dispatch lines name 26 programs
  (0x11d04f8000 … 0x9098eb200).
- None of its end-of-pipe writes landed:
  - its first, at 78, writes 0x1200006ee0, whose value is another one;
  - the counter at 0x11e1024040 holds …3b03e, one below the acb's first value …3b03f at 1534.
- Its 7 `WAIT_REG_MEM64`s were served on the CPU ("0 kept for the GPU"). So it waited on no GPU label.
- Evidence: High.

**It ran on the GFX ring.** The fence file shows only gfx_0.0.0 in use, with 2 jobs emitted and not signaled. The acb
was synced at t 427.638, after the dcb (427.284).
- Its "TIMEOUT 2039 ms" is its own 2-s host wait running out while it queued behind #412352. The hardware ring holds
  2 jobs (amdgpu's `sched_hw_submission`, default 2: TODO(verify) on 7.2.11), so it was most likely still in the
  scheduler.
- **It neither waits on the dcb nor hangs on its own.** It is collateral.
- TODO(verify): this may also be the reading of 16:32's dcb+acb pair (#1264477/#1264478), which exp 0403 §1 left

- `BC5_DIRECT_ACB_INHERIT=journal`: the play has **0** `acb inherit (exp 0403)` lines. Its 226 census lines report

## Proposed switches

The fixes-first rule applies: all of these go into one private build, each behind its own default-off switch. Ranked by
what they settle, cheapest first within equal value. **A** marks a catcher, **F** a fix candidate, **D** a diagnostic.

**A1. `BC5_DIRECT_FL_PROBE_STATE=1`** (catcher; CPU at the timeout only; nothing changes on the GPU).
- At a fence timeout, for the first draw that was issued and not done, and for the last fast-launch draw done before
  it, `fl_probe` prints the tracked NGG state the probe already holds:
  - `GE_MAX_OUTPUT_PER_SUBGROUP`, `VGT_GS_MAX_VERT_OUT`, `VGT_GS_OUT_PRIM_TYPE`, `VGT_GS_ONCHIP_CNTL`,
    `GE_NGG_SUBGRP_CNTL`;
  - `VGT_ESGS_RING_ITEMSIZE`, `VGT_GS_MODE`, `PA_CL_NGG_CNTL`;
  - `SPI_SHADER_PGM_RSRC1/2_GS`, `SPI_SHADER_IDX_FORMAT/POS_FORMAT`, `GE_USER_VGPR_EN`;
  - all 32 GS user-data words.
- It also prints the ring entry of the draw after the last one issued, head and tail. Head written would put the ME in
  that draw's copies; not written would put it in that draw's state loads.
- Evidence: §1 (the ME is in host [3047, 3316), packet unknown) and §2 (the limits were not read at the draw).
- Cost: lines at a timeout. Risk: none on the GPU.

**A2. A wave dump at the hang** (catcher; box-side; root; the maintainer's tool, not a build switch).
- bc5-gpu-watch or the root hang-dump helper reads the registers first and then the SQ wave state before the reset:
  - which waves are resident, of which program;
  - their PC and EXEC;
  - whether they wait at `s_sendmsg` GS_ALLOC_REQ, at an export or at `s_waitcnt`.
- This decides H1 directly: under H1, the GE waits for a subgroup's allocation or exports that never come.
- Evidence: §2 (SPI busy, SC idle).
- Cost and risk: root and umr. F208's helper halted waves before reading registers, so registers must be read first.
  The maintainer decides.

### Question

Can a subgroup of ES 0x11d01345, 0x11d00f85 or 0x11d00f8d emit 0 vertices and 0 primitives, so as to hit Mesa's GFX10

### Result

| Program | Instructions | GS_ALLOC_REQ | `s_trap` before it | Exports | Backward branches |
|---|---|---|---|---|---|
| 0x11d0134500 | 1000 | 1, line 961 | 2 (lines 47, 54) | prim 1, pos0 1, param 4 | 0 |
| 0x11d00f8500 | 266 | 1, line 85 | 2 (51, 58) | prim 1, pos0 1 | 0 |
| 0x11d00f8d00 | 307 | 1, line 86 | 2 (52, 59) | prim 1, pos0 1, param 2 | 0 |
| 0x11d00cde00 | 449 | 1, line 418 | 0 | prim 1, pos0 1, param 4 | 0 |

None of the four writes memory (0 stores and 0 atomics), and none jumps indirectly.

**1. The allocation is never 0/0. High for the listed code.**
- 0x11d01345, 0x11d00f85 and 0x11d00f8d:
  - The counts come from **one 32-bit header per meshlet**, loaded with a scalar buffer load.
  - Primitives = bits 31:24 + 1, so 1–256. Vertices = bits 23:17 + 1, so 1–128. Bits 16:0 locate the meshlet's index
    data.
  - The code also carries the "primitives 0 → vertices 1" guard, which Mesa's rule implies. It cannot trigger here,
    because the primitive count is at least 1.
- 0x11d00cde allocates a constant 48 primitives and 32 vertices.
- Only the group's first wave sends the message (SGPR s3 bits 27:24 = 0; TODO(verify) the system SGPR's name in this
  ABI). Every wave reaches that point:
  - 0x11d01345's one long skip (line 90, taken by a wave with no vertex lanes) lands at about line 951 (`isa1954.py`'s
    estimate, within an instruction or two). That is before the allocation at 961 and the exports.
  - There is no loop, so every wave ends.

**2. Nothing culls.** Primitives are exported by the threads with an index below the primitive count. Each primitive
packs three 5-bit vertex indices, and no culling or compaction is applied. Positions and parameters are exported by
the threads below the vertex count. So "366 points, all culled" cannot happen in this code: each point launches one
group, which exports its header's counts. **H1 (Mesa's GFX10 0-primitive hang) is not supported.** High for the listed
code; Medium overall (currency).

**3. What decides the exported counts is data read at execution time,** for 0x11d01345:
- user data 0–3 (s[8:11]): the object table, indexed with the group's first id; it gives an object record index;
- user data 12–15 (s[20:23]): a path flag at +0 and a start at +4. When the flag is not 0, ids come through an index
  buffer;
- user data 16–19 (s[24:27]): a table with V#s at +0x540 (that index buffer), +0x620 (64-byte object records) and
  +0x5a0 (the meshlet headers);
- user data 20 (s28): a base id, added to the point index on the direct path;
- the object record: +0x14 the header base, +0x18 the meshlet count, +0x1c flags;
- the meshlet header itself.

0x11d00f85 and 0x11d00f8d have the same structure, one table lower:
- user data 8–11 hold the path flag;
- user data 12–15 the V# table (+0x540, +0x620, +0x5a0);
- user data 16 the base.

Corrections to §2:
- With USER_SGPR 21, user data 21–31 never reach these shaders. So the hung draws' "user data 20–27 all zero" acts
  only through user data 20 (base id 0), and 22:54's earlier draws had 0 there too.
- For 0x11d01345, the crumbs' copy at "s[8:9]" (user data 8–9 = shader s[16:19]) is a constants table read in the
  vertex body. It is not the meshlet control path, so **the crumbs did not capture the inputs that decide the counts.**

**4. Two leads the code does show** (Low; to settle, not facts):

*H2: a bad header or index.*
- The header encoding allows up to 256 primitives and 128 vertices.
- The programmed limits are smaller:
  - the vertex indices are 5 bits, so up to 32 vertices;
  - the carried `GE_MAX_OUTPUT_PER_SUBGROUP` is 32;
  - `GE_NGG_SUBGRP_CNTL` PRIM_AMP_FACTOR is 64;
  - exports go one per thread.
- Garbage or stale header data, or a wrong meshlet index, would request counts that the group's threads do not export,
  or that exceed the programmed limits.
- Mesa documents another count rule whose breach hangs the hardware: 0 vertices requires 0 primitives
  (`ac_nir_lower_ngg_gs.c:819`).
- TODO(verify) whether an allocation that the exports do not match, or that exceeds those limits, hangs gfx1013. Also
  TODO(verify) the number of threads in a fast-launch group.

*H3: an assertion fires before the allocation.*
- 0x11d01345, 0x11d00f85 and 0x11d00f8d each execute `s_trap 1` before GS_ALLOC_REQ when:
  - the object record's flag bit 6 (+0x1c) is clear, or
  - the meshlet index is not below the record's meshlet count (+0x18).
- The carried `SPI_SHADER_PGM_RSRC2_GS` has TRAP_PRESENT 0 (gfx10.json bit 6). What `s_trap` does without a trap
  handler is TODO(verify) (AMD RDNA 1 ISA guide, S_TRAP):
  - a no-op leads to H2 with the bad index;
  - a stalled wave never sends its allocation, and the GE waits.
- Both readings start from the same trigger: bad per-object or per-meshlet data at execution time.

### Verdict and what would settle it

H1 is not supported by this code. The open question becomes H2/H3: whether the hung group read an invalid object record,
meshlet index or meshlet header.

1. **A4. `BC5_DIRECT_FL_MESHLET_PROBE=1`** (catcher; CPU at the timeout; no GPU change).
   - For the draws issued and not done, follow these programs' addressing for every point:
     - the path flag, the index buffer, the object id and record, and the meshlet header;
     - the patterns of 0x11d01345 and of 0x11d00f85/0x11d00f8d, selected by ES.
   - Print counts only:
     - the points whose record has flag bit 6 clear;
     - the points whose index ≥ the meshlet count;
     - the maximum header counts, and the headers above 32 vertices or 64 primitives.
   - Its data is read about 2 s late. Meshlet data is most likely static (TODO(verify)), so this is Medium, not High.
2. **A GPU-time variant, crumbs extension.** `COPY_DATA` the object record and the first meshlet headers of the draw
   instead of user data 8–9's first 32 bytes, for ES 0x11d01345 and 0x11d00f85/0x11d00f8d.
3. **A2, the wave dump.** It decides H3 directly: is a wave resident at a trap, or at an export, or is no wave resident?
4. Two reads:
   - `S_TRAP` with no handler, from the RDNA 1 ISA guide;
   - the current bytes of the three programs, as a hash against the 10-15 listings.
