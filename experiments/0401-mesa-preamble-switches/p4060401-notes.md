# p406: exp 0406's code switches (exp 0401 series e9)

**Why.** Exp 0406 (`experiments/0406-safeguard-cost-audit/README.md`, branch `exp/0406-safeguard-cost-audit`, commit
f3f8803f, section "Proposed test build: 0406 = e8 + three code switches"; detail in `raw/audit0406-logging.md` §1.3,
`raw/audit0406-memory.md` item 16 and `raw/audit0406-host.md` item 1) ranks the safeguards that cost time. It proposes
three code switches for one test build, each default off. This is that build's p406 part:
- `BC5_0406_LEARNED_PRUNE` and `BC5_0406_AUDIO_SLEEP` are built;
- `BC5_0406_PROBE_LAZY` is not, because its premise does not hold in the code. The top's rule of 2026-11-05: a switch
  whose premise fails is left out, not worked around.

Each built switch reads unset, empty and `0` as off and any other value as on (bc5::env_on's reading, F767; R41).
`BC5_0406_LEARNED_PRUNE` has two on modes: `eager` is the eager-heap skip alone; any other on value (`1`) is the skip
plus the junk drop. Each switch is read once and prints one line that names its mode. With no 0406 word set, the
binary does what e8's does, except for one journal line a minute (below).

Line references: `U:` is e8's main unit `src/libs/bc5LleAgc.cpp` (bd181169), `A:` e8's `src/libs/audio.cpp` (1f90e752),
`D:` `backend/src/direct.cpp` (51279eae, this worktree at 2923fbd5).

## `BC5_0406_PROBE_LAZY`: not built

The spec: stop copying `ib_copy` and `ran_copy` at every async submit, and at a fence timeout copy them from the job's
submitted buffer, "which the job still owns because its fence has not signalled". It marks that ownership TODO(verify).
The code says no:
- *The job owns no copy of its own.* `PendingJob` (U:10169-10186) holds `ib`, a pointer (U:10173), and the device's
  `slot` (U:10180). `ib_copy` is the only copy of the bytes it has.
- *With chains, the pointer dangles at the timeout.* Exps 0396/0399's manifests (`W1.manifest.txt`, `Z1.manifest.txt`)
  show `BC5_DIRECT_CHAIN=2` and `BC5_DIRECT_STAGE=all` in the play env; today's box files were not read (TODO(verify)).
  - Every buffer then leaves through `chain_submit`'s local `Chain mine` (U:5299), as `submit_now(mine.buf.data(), …)`
    (U:5327).
  - `submit_now` keeps only the pointer (`it.job.ib = ib`, U:11977), queues the job (U:11999) and returns. `chain_submit`
    returns too, and `mine.buf` is freed.
  - The completion thread waits up to 2 s in `finish` (U:10551, U:10559), and its timeout probe (U:10633) comes after.
- *The other buffers the copy is made from are locals.* Without crumbs the probe copies `sub_ib`: the mec rebuild's
  `mec_ib` (U:11774) or `ib` (U:11776). With crumbs it copies `ib`, and `fl_ib` (U:11855) is a local as well. The
  executed offsets (`ran_copy`) come from the local result `r` (U:11879); nothing else keeps them.
- *The device's slot survives, but it holds other bytes.* The slot stays reserved through a timeout: its sequence is set
  at submit (D:1606), and only a `finish` that went well frees it (D:1708). But it holds the filter's output, not what
  `ib_copy` holds:
  - its content is the prologue, `policy::filter`'s buffer with drops NOP-ed and rewrites (D:1126-1130), the nested
    pieces (D:1380-1420) and the epilogue;
  - `bc5/direct.hpp` has no accessor for it;
  - the executed offsets need the filter's input too (`executed_offsets_of`, D:979, D:1130).
- *Without chains* the pointer is the title's guest buffer: readable, but the title's, not the job's.

The spec's fallback is a ring of the last 32 jobs' copies. It would still copy at every submit, which is the cost the
switch exists to remove. So the switch is left out. The spec's other half, reading `BC5_DIRECT_TIMEOUT_PROBE` once
instead of a `getenv` per submit (U:11978), belongs to the same switch and is not built either. Exp 0406 can propose it
on its own.

## `BC5_0406_LEARNED_PRUNE` (main unit)

**The switch.** It is read at the first `learned_load`. The coordinator split it into two modes after the first build,
because the junk drop removes zero pages from windows the GPU once faulted on (below), which is too risky for the lean
profile and an unattended series:
- `BC5_0406_LEARNED_PRUNE=eager`: the eager-heap skip alone. Every learned window stays loaded and scratch-filled as
  today;
- `BC5_0406_LEARNED_PRUNE=1`, or any other on value (the full mode): the skip and the junk drop;
- unset, empty and `0` are off. The minute count runs in every mode.

One journal and stderr line names the mode:
- `exp 0406 (p406): learned prune on, mode eager (BC5_0406_LEARNED_PRUNE=eager): map_window left out for windows inside
  eager heaps, the junk windows kept and filled as e8; …`;
- `exp 0406 (p406): learned prune on, mode full (BC5_0406_LEARNED_PRUNE=1): windows at junk addresses dropped at load,
  map_window left out for windows inside eager heaps; …`. Another value says so: `…=yes, any value but unset, empty, 0
  or eager is the full mode`;
- `… off (BC5_0406_LEARNED_PRUNE unset|empty|=0): as e8; …`.

The parse is exact: only `eager` is the eager mode. `Eager` or `eager ` is the full mode.

**At load, full mode only: the junk windows leave the list.** After `learned_load` reads the file (U:4018-4028), the windows at junk
addresses leave `g_learned`: a base with a bit at 40 or above set, or a base of 0. The file is not changed. One line:
`learned prune (exp 0406 p406): 107 learned windows loaded, 75 kept, 32 dropped at junk addresses (31 with a bit at 40
or above set, 1 at base 0); the file is unchanged`.
- *The count.* Exp 0288's README (lines 57-60) says 46 junk windows. By the rule as exp 0406 writes it, its list
  (`experiments/0288-emulator-memory/raw/direct-learned-pkg-20261024.txt`) has 32. Its 46 also counts 14 windows below
  2^40 that lie outside the 0x11xx–0x12xx heap span and the AMM window: 0x13–0x17xx, 0x2672…, 0x5452…, 0x7ffe… and
  0x820a–0x8516…. Those 14 stay.
- *What the drop changes.* `map_window` imports nothing for these windows. No view of direct memory lies there, and no
  VMA either: `sync_mappings` keeps only VMAs below 0xfbffffffff (U:3819, U:3836). But `scratch_fill` (U:4187) maps the
  2-MiB zero buffer over every hole of a window below 2^47 (U:4189-4191):
  - 8 of the 32 lie at or above 2^47: dropping them changes nothing;
  - the other 24 lose their zero mappings: 23 with bits 40–46 set (48 pieces of 2 MiB each, VA only, no RAM), and the
    one at 0;
  - a GPU read there then faults instead of reading zeros;
  - the window at 0 is F208's: the geometry engine's reads of pages 0–0x2f000, whose bursts once reset the box (F213,
    run 800). F248 traced them to `VGT_TF_MEMORY_BASE` = 0 and removed them with `BC5_DIRECT_GC_TF_RING=1`, which the
    0396/0399 manifests show in the play env (TODO(verify) on today's `bc5-run.env`).
  - This is exp 0406's "drop" taken at its word. The arms' "no new hang class" reading is what covers it.
- *A fault re-learns a window.* A fault at a dropped window's address makes `learned_add` (U:4102) find it missing. It
  then appends the window to the file again (a duplicate line) and maps it for the rest of the run.

**In `learned_apply`, both modes: `map_window` left out for a window inside an eager heap.** Exp 0406's session asked that this
premise be shown in the code: the import of a window that lies wholly inside an eager heap is a no-op today. It holds.
`map_window` (U:4122) does three things:
1. `direct_force` (U:3768) puts the window's chunk offsets into `S.forced`, and when any were new it runs a forced
   `direct_sync_one`.
   - There, every chunk of an eager view is in `need` already (U:3536).
   - A forced chunk goes through the same two tests, the zero list and "already covered" (U:3555).
   - `ZLearned` keeps zero-listed chunks skipped (U:4123).
   - So forcing adds no import and no BO.
2. The userptr part maps pieces of anonymous VMAs only (`g_vmas`: no path, inode 0, U:3836-3840). A view of direct
   memory is a mapping of the memfd, so no such VMA lies under it, and nothing is mapped.
3. `have` is read again only when (1) asked for something.

So the call adds no BO, and the mapping list is the same before and after.

The skip needs the memfd (`dstate_fd(g_d[0]) >= 0`) and sorted views (`DViews::sorted`), so that no other view overlaps
the window. It uses the views the pass pinned (`t_pinned_views[0]`), the same ones `direct_force` sees. The window's
`scratch_fill` stays as it is; that line is not touched. Inside an eager heap it fills nothing, because the heap is a
guest range (U:4218).

There is one lasting difference. `S.forced` is never emptied: the unit has no erase of it. Today the window's chunks stay
forced for the rest of the run; with the skip they are never forced. This matters only:
- if the eager view goes away before a chunk under it was imported (an AMM unmap, a heap freed). Today the forced loop
  still imports that chunk, under no view;
- for the lazy release (`BC5_DIRECT_LAZY_RELEASE`, not in the e8 shortcut), which never cuts a forced chunk;
- after a device reopen, when today's forced chunks are imported again whether a view covers them or not.

In none of these does a GPU mapping differ: `S.maps` follows the views. The difference is which BOs stay pinned.

The first time each window is left out, one line: `learned prune (exp 0406 p406): window 0x…+0x6000000 lies inside eager
views (the first: <name> at 0x…+0x…): map_window left out while it does; its scratch fill stays`.

**The minute count, on and off.** At the call site, right after `learned_apply` (U:11221-11223), every call is counted,
and with it the calls over 5 ms (the same bound as `learned_apply`'s own line, U:4297), their time and the longest.
Once a minute has passed since the minute's first call, one line:
`learned apply (exp 0406 p406): t N s: K of M calls in the last 60 s over 5 ms, X ms in all, the longest Y ms; A over 5
ms so far, B s in all; learned prune on|off, S windows left out of map_window so far`.
- Exp 0406 asks for this count in both arms, so with the switch off this line is the one thing the binary adds to e8.
  That is the accepted exception.
- Submissions drive it: a minute with no submission has no line.

**The quiet journal.** Under `BC5_DIRECT_JOURNAL_QUIET=1` every new line is kept (kind 0 of `journal_quiet_kind`,
U:1807):
- none starts with `timing: `, `acb rest ` or `submit #`;
- none holds `at the timeout`;
- each is shorter than the filter's 1,024 bytes.

The test checks each line with cap's real filter.

**Costs.**
- *Off:* one flag test per window per pass, one in `learned_load`, and one mutex with a few counters per submission
  (the minute count).
- *On:* the drop (full mode) runs once, at load. The skip (both modes) costs a binary search in the pinned views and a walk of the views under the
  window: one view for a heap, up to seven for 16-MiB AMM views. It saves that window's `map_window`, which walks the
  whole mapping list. Exp 0288 measured the window loop at 6.4 ms of a 7.6-ms call over 21,572 mappings
  (`raw/M2-breakdown.txt`).

**Risks.**
- The zero pages (full mode only) and the forced set (both modes), above. `eager` is the mode without the zero-page
  risk.
- Exp 0288's list is from 2026-10-24. The run's own learned file (`BC5_DIRECT_LEARNED`, per run) may differ: read its
  load line in the arms.

## `BC5_0406_AUDIO_SLEEP` (audio.cpp)

**The switch.** One stderr line (audio.cpp has no journal):
- `[bc5] exp 0406 (p406): audio sleep on (BC5_0406_AUDIO_SLEEP=1): the blocking wait sleeps the drain time, 500 us to
  2 ms`;
- `… off (BC5_0406_AUDIO_SLEEP unset|empty|=0): the 500-us poll`.

**What it does.** `QueueSdlAudio`'s blocking wait (A:972-1007) polls the queue every 500 µs (A:1003). With the switch
on, `Bc5AudioSleepWait` runs first, inserted before the old loop:
- it makes the old loop's checks in the old loop's order: a queue at or under the mark ends it; more than 1 s since
  `wait_start` clears the queue (`tr_clears++`);
- each sleep is (queued − mark) ÷ the device's bytes per ms (its spec: freq × channels × bits ÷ 8000), rounded up and
  held between 500 µs and 2 ms.

The old loop then runs as it was. Only this thread queues to the port, and SDL's callback only takes from it, so the
queue is at or under the mark (or cleared), and the old loop's first test ends it. That costs one more
`SDL_GetQueuedAudioSize` per call, about 94 a second, against the ~2,000 polls a second it replaces. The old loop's lines
are unchanged; the edit only inserts.

**Ports.** It covers every port that takes the blocking wait: every port but the pad-routed and `pad_nb` ones, the same
set the old loop serves.

**Deviation: the 500-µs floor.** The spec says "the computed drain time (capped at 2 ms)". Without a floor, a queue a few
bytes over the mark gives sleeps of a few µs, so more wake-ups than today. With the floor, the switch never wakes more
often than the old poll. It ends at most 2 ms after the queue reaches the mark; the mark holds at least two buffers.

**TODO(verify).** SDL hands the queue to the device in callback-sized pieces, so the computed time is the earliest the
queue can reach the mark. The 2-ms cap bounds how late the wait ends either way.

**The audio rule.** This is an audio change. Before any play with it on, it needs:
1. experiment 0372's software replug check: `s6n0372.sh` with `replug0372.sh`, P1 (three pulls) and P2 (`late`);
2. then the maintainer's physical replug and a DualShock 4.

It is not in the frame-rate arms: it is exp 0406's separate audio arm.
